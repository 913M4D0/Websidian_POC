# Websidian 발표대본

## 발표 운영 기준

- 총 15분 발표, 질의응답 5분 기준입니다.
- 서론 4분 10초, 본론과 시연 7분 55초, 결론 2분 55초로 구성합니다.
- 화면의 이슈 294건, 연결 자료, 파일 경로와 처리 기록은 모두 합성 데이터입니다.
- 294건은 기능 시연 범위이며 도입 효과를 검증한 표본이 아닙니다.
- Websidian의 정확한 정의는 `이슈 중심 혼합 관계 탐색 POC`입니다. Microsoft GraphRAG를 구현했다고 표현하지 않습니다.
- 오른쪽 화살표 또는 Space는 다음 요소, 왼쪽 화살표는 이전 슬라이드, F는 전체 화면, N은 발표자 메모, R은 참고 자료, B는 백업 시연입니다.

## 발표 전 체크리스트

1. 발표 HTML과 Websidian 서비스 탭을 모두 열고 브라우저 알림과 로그인 화면을 닫습니다.
2. 발표 HTML을 1번 슬라이드에서 시작하고 F로 전체 화면을 켭니다.
3. Websidian에서 WS-008이 진행 상태인지 확인합니다. 완료 상태라면 시연 전에 다시 진행 상태로 복원합니다.
4. WS-008의 `이슈 분석`, `테스트 케이스`, `처리 완료` 동작을 확인합니다.
5. OpenRouter 연결 상태를 확인합니다. 첫 출력까지 시간이 걸릴 수 있으므로 대기 중에는 연결된 근거 이력을 설명합니다.
6. 실시간 호출이나 네트워크에 문제가 생기면 발표 HTML로 돌아와 B를 눌러 백업 시연을 진행합니다.
7. PDF도 별도 창에 열어 둡니다.

## 전체 흐름

- 서론: 완료한 이슈의 판단 근거가 다음 이슈로 이어지지 않아 같은 조사를 반복하는 현업 문제에서 출발하고, 기록 사이의 관계 인덱스가 없다는 원인을 도출합니다.
- 본론: 일반·벡터 검색과 그래프 관계 탐색의 역할 차이를 설명하고, Websidian의 해결 구조와 실제 화면을 보여줍니다.
- 결론: 기대효과를 측정 가능한 가설로 제시하고, 현재 POC의 한계와 다음 검증 단계를 분명히 합니다.

### 7. 일반·벡터 검색과 그래프 탐색 — 4:10-5:20

화면 큐: 왼쪽 Top-K 결과를 먼저 보여주고, 다음 클릭으로 오른쪽 1-hop·2-hop 경로를 표시합니다. 마지막에는 하단 참고 문구를 가리킵니다.

발화:

여기서 제가 공유드린 GraphRAG 영상의 문제의식을 가져오겠습니다.

일반 검색과 벡터 검색은 질문과 가까운 후보를 찾는 데 매우 유용합니다. 왼쪽처럼 키워드나 의미가 비슷한 결과를 Top-K 순서로 빠르게 보여줍니다. 이 방식이 틀렸다는 뜻은 아닙니다.

하지만 현재 이슈와 표현은 다르면서, 중간의 공통 자료나 다른 이슈를 통해 연결되는 기록은 순위만으로 설명하기 어렵습니다.

Microsoft GraphRAG 문서도 기존 벡터 유사도 중심 검색이 흩어진 정보의 공통 속성을 따라 연결하거나 전체 맥락을 묻는 질문에서 어려울 수 있다고 설명합니다. Local Search는 관련 엔티티를 진입점으로 삼아 이웃과 관계, 원문으로 탐색 범위를 넓힙니다.

오른쪽의 그래프 탐색은 바로 이 차이를 보여줍니다. 1-hop의 중간 기록을 거쳐 2-hop의 추가 맥락까지, 무엇이 비슷한지만이 아니라 무엇을 따라 확인해야 하는지를 보여줍니다.

그래서 Websidian은 목록 검색을 버리지 않습니다. 일반 검색으로 후보를 찾고, 관계 그래프로 후보 사이의 연결 이유와 원문 경로를 보존합니다.

정확히 말씀드리면 Websidian은 Microsoft GraphRAG 구현이 아닙니다. 이 문제의식을 이슈 관리에 적용한 이슈 중심 혼합 관계 탐색 POC입니다.

- [Microsoft GraphRAG 공식 개요](https://microsoft.github.io/graphrag/)
- [Microsoft GraphRAG Local Search](https://microsoft.github.io/graphrag/query/local_search/)

### 9. Websidian의 해결 구조 — 6:25-7:20

화면 큐: 연결된 그래프를 2초 보여준 뒤 네 원칙을 표시합니다.

발화:

이 원리를 이슈 처리 흐름에 적용한 것이 Websidian입니다.

첫째, 모든 노드는 이슈입니다. 새 이슈와 연결됐다고 과거 이슈의 ID, 제목, 본문, 처리 기록이 바뀌지 않습니다.

둘째, 텍스트와 공유 자료를 기준으로 완료 이력을 좁히고, 호환되는 임베딩이 있을 때 의미 이웃을 선택적으로 보강합니다.

셋째, 현재 이슈에서 직접 연결된 1-hop과 그 이력에 연결된 2-hop을 펼쳐 연결 이유와 원문을 함께 보여줍니다.

넷째, AI는 자동으로 모든 것을 결정하지 않습니다. 사용자가 요청할 때만 화면에 연결된 완료 이력 안에서 이슈 분석과 테스트 케이스 작성을 보조합니다.

즉 AI가 답을 먼저 만들고 근거를 끼워 맞추는 것이 아니라, 근거를 먼저 연결하고 AI는 그 위에서 일합니다.

## 예상 질의응답

### 1. 기존 검색이나 벡터 검색과 무엇이 다릅니까?

기존 검색을 대체하지 않고 함께 사용합니다. 현재 POC의 기본 검색은 이슈 원문과 활동, 처리 결과의 텍스트 및 공유 자료를 비교해 후보를 순위화합니다. 호환되는 임베딩이 있으면 의미 유사도를 선택적으로 보강합니다. 그래프는 이 직접 결과에서 2-hop으로 확장해 중간 이슈와 연결 이유, 원문 경로를 함께 보여줍니다. 검색은 가까운 후보를 찾고 그래프는 무엇을 따라 확인할지 보여준다는 차이입니다.

### 2. Microsoft GraphRAG를 적용한 것입니까?

아닙니다. Websidian은 Microsoft GraphRAG 구현이 아니라 이슈 중심 혼합 관계 탐색 POC입니다. GraphRAG가 제기한 벡터 Top-K의 연결 한계와 엔티티 이웃 탐색 원리를 참고했지만, 엔티티·관계 자동 추출, 커뮤니티 탐지·요약, GraphRAG Global·Local Search를 그대로 구현하지 않았습니다.

### 3. 연결선은 어떤 기준이며 원인을 의미합니까?

원인을 의미하지 않습니다. 기본 관련 순위는 이슈 텍스트와 공유 자료를 결합하고, 명시적 참고 이슈와 선택적 의미 이웃을 보강합니다. 1-hop과 2-hop은 탐색 깊이입니다. 유사도, 공유 자료, 시간 근접성은 모두 관련성 신호이며 정답이나 인과관계의 증명이 아닙니다.

### 4. AI가 잘못된 내용을 기억하면 더 위험하지 않습니까?

원본 이슈는 수정하지 않습니다. 완료하면 원문 기반 기억 노드를 먼저 만들고, AI가 생성한 파생 기억은 별도 저장합니다. 허용된 근거 ID, 원본 revision과 hash, 정해진 구획의 완결성을 검사하며 실패하면 AI 파생 결과를 저장하지 않습니다. 형식 검증은 사실성 보증이 아니므로 근거 이슈 ID와 원문 접근 경로를 항상 남깁니다.

### 5. AI가 실패하면 이슈 완료나 기억 생성도 멈춥니까?

멈추지 않습니다. 분석과 테스트 케이스는 선택적 보조 기능이고, 완료와 원문 기반 기억 생성은 분리되어 있습니다. AI 호출이나 파생 기억 검증이 실패해도 처리 결과와 원문 기반 기억 노드는 유지됩니다.

### 6. 개인정보와 영업기밀은 어떻게 보호합니까?

현재 시연 데이터는 전부 합성입니다. 현업 파일럿 전에는 사내 배포 위치, 자료별 ACL, 사용자 권한, 마스킹, 외부 전송 범위, 감사 로그, 보존·삭제와 백업 정책을 먼저 확정해야 합니다. 현재 POC가 이 운영 보안을 해결했다고 주장하지 않습니다.

### 7. GitHub 전용 서비스입니까?

아닙니다. 핵심 구조는 이슈 등록, 관련 이력 탐색, 처리 완료, 기억 생성의 반복입니다. GitHub는 형상기억 도구 연동의 한 예시이며 현재는 수동 단방향 스냅샷 가져오기만 구현했습니다. 웹훅, 예약 동기화, 양방향 쓰기는 후속 범위입니다.

### 8. 정량 성과가 아직 없는데 효과를 어떻게 검증합니까?

294건은 기능 흐름과 시각화를 위한 합성 데이터입니다. 제한된 현업 파일럿에서 첫 유효 이력 도달 시간, 과거 근거 재사용률, 반복 조사와 중복 수정 건수, 회귀 확인 누락, 타팀 영향 후보 발견 시점을 기존 방식과 같은 조건으로 비교하겠습니다.

### 9. 이슈가 수만 건으로 늘어나도 동작합니까?

현재는 294건에서 흐름과 화면 경험을 검증했습니다. 전사 규모에서는 전용 벡터 또는 그래프 저장소, 증분 색인과 재색인 큐, 권한 필터, 대량 렌더링 최적화, 관측성과 비용 관리, 백업·복구 검증이 필요합니다.

### 10. 왜 3D 그래프가 필요합니까?

목록은 개별 이슈를 찾고 읽는 데 유리하며 그래프는 타팀 변경이나 공통 자료처럼 여러 이슈에 걸친 탐색 경로를 파악하는 데 유리합니다. 3D 성운은 전체 조직 기억의 규모와 연결성을 한눈에 보여주는 시각화이고, 실제 업무에서는 이슈를 선택하면 관련 경로만 정렬하고 목록과 원문을 함께 사용하도록 구성했습니다.
