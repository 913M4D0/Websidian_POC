  - 접수 마감: `2026-09-11 16:00`
  - 발표자료: `PPT/PPTX/PDF/HTML`, 합산 50MB 이하
  - `PDF 필수`
  - 실제 화면·영상·서비스·캡처 형태의 데모 자료 필수
  - 참고자료는 최대 5개, 파일당 20MB
- 세부 배점은 운영방안 PDF의 AX 심사표를 사용합니다.
- 합성 이슈 294건은 기능·성능·시각화 시연 데이터이며, 실제 업무 성과로 계산하지 않습니다.
- 숫자는 목표치와 실측치를 명확히 구분합니다. 결과가 기대보다 낮더라도 원자료와 표본 수를 함께 공개하고 수치를 만들지 않습니다.
- 현재 소유자 전용 배포 URL은 발표자용으로만 사용하며, 심사 제출 링크로 사용하지 않습니다.
- 소스코드와 합성 데이터는 공개할 수 있으며, 제출 시점의 tag/release로 고정합니다.
- 실제 키움증권 업무 데이터·이슈·구조·로그는 POC에 사용하거나 제출하지 않습니다.

### 0.1 공개성과 보안을 함께 증명하는 기본 입장

Websidian은 다음 문장을 모든 제출물의 공통 전제로 사용합니다.

> 증권 서비스 운영 이력에는 고객·거래·장애·내부 시스템 구조와 같은 민감정보가 포함될 수 있어 실제 업무 자료는 외부 AI나 공개 심사자료에 사용하지 않았습니다. 대신 실무에서 발생할 수 있는 문제 구조를 재현한 완전 합성 데이터로 POC를 구성하고, 소스코드·평가 방법·익명화된 측정 결과를 공개해 적용 가능성을 검증했습니다.

이 접근의 핵심은 “보안 때문에 검증하지 못했다”가 아니라 **검증 가능한 범위를 보안 경계 안에서 다시 설계했다**는 것입니다.

발표용 권장 문안:

> 저는 키움증권 SM 업무를 수행하며, 문제 하나를 처리할 때 코드보다 과거의 결정과 변경 이유를 찾는 데 더 많은 시간이 드는 상황을 반복해서 보았습니다. 다만 증권 서비스의 운영 이력은 고객·거래·장애·내부 시스템 정보를 포함할 수 있어 실제 업무 이슈를 발표자료나 외부 AI에 사용할 수 없습니다. 그래서 실제 사건을 가져오는 대신 업무에서 마주치는 문제 구조와 난이도를 294개의 완전 합성 이슈로 재현했습니다. 그리고 기존 목록·검색 방식과 Websidian을 동일 조건에서 비교해 탐색 시간, 핵심 근거 발견률, 회귀 테스트 조건, 토큰과 비용이 얼마나 달라지는지 측정했습니다. 아래 결과는 키움증권의 실운영 실적이 아니라, 누구나 확인하고 다시 실행할 수 있는 실무 유사 POC 관측값입니다.

- 실제 이슈를 익명화해서 옮기는 방식도 사용하지 않습니다. 원문 복원 가능성과 내부 구조 유출 위험이 있기 때문입니다.
- 24개 대표 이슈와 270개 배경 노드는 실존 사건·고객·파트너·시스템명을 복제하지 않은 합성 데이터로 고지합니다.
- 정량 결과는 `키움증권 실운영 성과`가 아니라 `실무 유사 합성 POC 조건에서 관측한 결과`로 표기합니다.
- 결론은 “현업 적용이 완료됐다”가 아니라 “현업 적용 가능성과 기대 개선 폭을 통제된 POC로 검증했으며, 실제 도입 전 사내 보안 환경 파일럿이 필요하다”입니다.
- 회사명과 직무는 문제를 발견한 배경을 설명하는 데만 사용하고, 회사가 공식 도입·검증·승인했다는 인상을 주지 않습니다.

### 0.2 공개 전 데이터·소스 감사 범위

전체 공개 허용과 안전한 공개는 다른 문제이므로 아래 범위를 동결 전에 검사합니다.

- `.env*`, API 키, 토큰, 계정·이메일, 로컬 경로, 배포 로그
- `data/issues.json`, `data/github-issue-drafts.json`, `data/github-bindings.json`
- 테스트 fixture, README 예시, 화면 캡처, 발표 HTML/PDF, Git 커밋 이력
- 실제 조직명·내부 시스템명·파트너명·장애 일시·운영 일정·URL·저장소명·파일 경로와 유사한 값

공개 저장소에는 `SECURITY.md`, `THIRD_PARTY_NOTICES.md`, 합성 데이터 고지, 평가 재현 명령, 제출 commit SHA를 포함합니다.

프로젝트 코드를 공개하는 것과 제3자에게 재사용 권한을 부여하는 것은 다릅니다. 코드 소유권·회사 규정을 확인하기 전에는 MIT/Apache 등의 `LICENSE`를 임의로 선택하지 않습니다. 확인 전 공개가 필요하면 소스는 열람 가능하게 두되 무라이선스 상태가 재사용 허가가 아님을 README에 명시하고, 의존성의 `THIRD_PARTY_NOTICES.md`는 별도로 제공합니다.

## 1. 100점의 공통 판정 원칙

각 주장은 아래 네 가지가 한 묶음으로 존재해야 완성으로 봅니다.

1. **문제**: 누가 어떤 상황에서 무엇 때문에 시간을 잃거나 위험을 감수하는가
2. **구현**: Websidian이 그 문제를 어떤 AI·검색·기억 흐름으로 해결하는가
3. **실측**: 같은 조건에서 기존 방식과 비교했을 때 시간·정확도·비용이 어떻게 달라지는가
4. **재현**: 심사위원이 PDF, 영상, 공개 데모, 원자료에서 같은 근거를 다시 확인할 수 있는가

발표 문구, 애니메이션, 기대효과만 있는 상태는 증거가 아닙니다. `주장 → 측정표 → 원자료/로그 → 재현 화면`이 이어져야 합니다.

### 1.1 심사위원 성향을 반영한 3층 전달 구조

심사위원을 단순히 “전문가/비전문가”로만 나누지 않습니다. 공식 심사 구성인 외부 전문가 40%, 내부 심사위원 40%, 심사 AI 20%에 더해, **업무·기술 경력은 깊지만 생성형 AI 경험은 적은 심사위원**을 별도 핵심 독자로 둡니다.

| 심사 관점 | 가장 먼저 보는 것 | 거부감을 만드는 것 | Websidian의 대응 |
|---|---|---|---|
| 일반·비기술 심사위원 | 문제가 실제인지, 화면이 쉬운지, 결과가 무엇인지 | LLM·임베딩·Top-K 같은 용어부터 시작하는 설명 | 한 문장 결론, 기존/개선 비교, 대표 이슈 한 건, 큰 실제 수치 |
| 내부 현업·경영 심사위원 | 조직의 시간·위험·인수인계 문제, 도입 가능성, 전사 확장 | 화려한 POC만 있고 실사용·보안·책임자가 없는 경우 | 파일럿 결과, 업무 수명주기, RACI, 단계별 확장, 비용 상한 |
| 외부 기술·AI 전문가 | 검색·생성 구조의 타당성, 평가 방법, 실패 처리, 재현성 | “AI가 알아서 연결한다”는 설명과 근거 없는 성능 주장 | 정답셋, Recall/인용 정확도, A/B, 모델·토큰 로그, fail-closed |
| 경력 많은 기술·업무 전문가 + AI 경험 적음 | 기존 개발·운영 원칙과 연결되는지, AI를 통제할 수 있는지 | 새 용어로 기존 경험을 무시하거나 AI가 판단을 대체한다는 인상 | 원문 불변, 버전, 변경파일, 롤백, 승인, 감사라는 익숙한 언어로 설명 |
| 심사 AI | 명시적인 문제·AI 방식·구현·성과·한계와 검색 가능한 수치 | 영상·애니메이션에만 존재하는 정보, 모호한 대명사와 과장 | PDF 본문에 항목명·수치·표본·조건·부록 쪽을 텍스트로 명시 |

모든 핵심 슬라이드는 다음 세 층을 동시에 가집니다.

1. **상단 한 문장 — 누구나 이해하는 결론**

   예: `294개의 기록을 모두 읽히지 않고, 현재 이슈와 연결된 근거만 찾습니다.`
2. **중앙 시각·실제 화면 — 현업이 확인하는 흐름**

   예: 신규 이슈 → 과거 롤백 이력 발견 → 위험한 수정 중단
3. **하단 증거띠·각주 — 전문가와 심사 AI가 검증하는 근거**

   예: `Top-K+2-hop · 입력 토큰 -78% · Recall@5 87.5% · n=24 · 부록 p.18`

이 방식이면 일반인은 결론만 읽어도 흐름을 놓치지 않고, 전문가는 같은 화면에서 근거의 위치를 찾을 수 있습니다.

### 1.2 용어 번역 규칙

발표에서는 쉬운 표현을 먼저 말하고 기술 용어는 괄호나 각주에 둡니다.

| 먼저 말할 표현 | 기술 표기 |
|---|---|
| 의미가 가까운 이력을 찾는다 | 임베딩 유사도 검색 |
| 직접 연결된 기록을 따라 한 단계 더 찾는다 | multi-hop / 2-hop graph traversal |
| 현재 이슈와 관계있는 기록만 AI에 전달한다 | retrieval-grounded context / Top-K context selection |
| 답의 근거가 된 원문을 함께 보여준다 | provenance / citation grounding |
| 검증에 실패하면 기억으로 확정하지 않는다 | validation gate / fail-closed |
| 같은 요청을 두 번 과금하지 않는다 | idempotency / cache |

`Graph RAG`, `벡터`, `에이전트`, `추론 토큰` 같은 말은 문제를 이해하는 데 꼭 필요한 경우에만 씁니다. 먼저 익숙한 업무 언어로 의미를 전달한 뒤 전문가용 명칭을 붙입니다.

### 1.3 연령·경험 차이를 견디는 발표 UI 규칙

- 본문은 최소 24px, 핵심 문장은 32px 이상을 기준으로 하고 작은 회색 각주에 핵심 정보를 숨기지 않습니다.
- 한 슬라이드에 핵심 메시지는 하나, 색상 의미는 최대 3개로 제한합니다.
- 애니메이션은 관심을 모으는 용도로만 쓰고, 움직임을 보지 못해도 같은 의미를 정지 화면에서 읽을 수 있게 합니다.
- 그래프는 “멋진 성운”과 “정보 전달 화면”을 분리합니다. 오프닝에서는 임팩트, 설명·시연에서는 기준 이슈·직접 관계·간접 관계의 3단계만 선명하게 표시합니다.
- 모든 수치는 큰 숫자와 한 문장 해석을 함께 둡니다. 예: `-38% · 첫 유효 이력을 찾는 시간이 줄었습니다.`
- 빨강/초록만으로 성공·실패를 구분하지 않고 아이콘·라벨을 함께 사용합니다.
- 발표자는 전문 지식을 가르치려는 어조가 아니라, 심사위원이 이미 아는 운영 원칙을 AI 시대에 확장한다는 어조를 사용합니다.

### 1.4 청중별 30초 방어 문장

- **“그래서 무엇이 좋아집니까?”**

  `같은 문제를 다시 조사하는 시간을 줄이고, 과거에 실패했던 변경과 타팀 영향을 처리 전에 발견합니다.`
- **“AI가 틀리면 더 위험하지 않습니까?”**

  `AI 출력은 원문을 바꾸지 않습니다. 근거 원문을 함께 보여주고, 검증과 사용자 승인에 실패하면 기억 노드로 확정하지 않습니다.`
- **“일반 검색이나 기존 이슈관리로 충분하지 않습니까?”**

  `기존 도구를 대체하지 않습니다. 시간·변경파일·의미 관계를 따라 여러 이슈에 흩어진 맥락을 연결하는 기억 계층을 추가합니다.`
- **“전사에 바로 쓸 수 있습니까?”**

  `현재는 합성 데이터 POC입니다. GitHub는 첫 어댑터이고, 권한·마스킹·운영 책임을 갖춘 1팀 파일럿부터 단계적으로 넓히는 계획입니다.`
- **“정말 효과가 있습니까?”**

  `기대효과가 아니라 같은 난이도의 과제를 기존 방식과 Websidian 방식으로 수행한 시간·발견률·오판 결과와 원자료를 보여드리겠습니다.`

파일럿은 실제 사내 이슈를 요구하지 않습니다. 동일 합성 데이터에 대해 `기본 목록·키워드 검색만 제공하는 기준선 모드`와 `그래프·AI를 제공하는 Websidian 모드`를 비교하면 보안 노출 없이도 도구가 만든 차이를 측정할 수 있습니다.

- 참여자가 현업 동료라면: 업무 판단 시간과 핵심 이력 발견률까지 측정
- 참여자가 비현업 사용자라면: 탐색 성공률·사용성만 측정하고 실무 효과로 확대 해석하지 않음
- 참여자가 없으면: 검색 정확도·토큰·지연·비용 같은 기술 벤치마크만 제시하고 사용자 생산성 향상이라고 표현하지 않음

통제 실험의 재현 조건:

- 대표 24건은 `3개 시나리오 × 8개` 평가군, 나머지 270건은 실제 탐색 난이도를 만드는 방해 노드로 고정
- 데이터셋 SHA-256, commit SHA, 실제 모델 ID, 프롬프트 버전을 실험 전에 기록
- 알고리즘 조정용 항목과 최종 평가 항목을 분리하거나, 시나리오 하나를 매번 평가용으로 남기는 방식으로 과적합 방지
- A/B 순서를 참가자별로 교차 배정하고, 답안은 가능하면 도구 조건을 가린 상태에서 2명이 같은 기준으로 채점
- 결과는 중앙값·개인별 변화·표본 수와 함께 표시하고, 소표본에서 통계적 유의성을 과장하지 않음

최소 파일럿 질문:

1. 첫 유효 이력을 언제 찾았는가
2. 처리 방향을 언제 확정했는가
3. 반드시 확인해야 할 과거 결정·롤백·타팀 변경을 찾았는가
4. 불필요한 개발 또는 위험한 수정을 피했는가
5. 일반 사용자도 핵심 흐름을 혼자 수행할 수 있었는가

### C. 제출 적격성 — 점수 이전의 탈락 방지 게이트

- 공식 제출 PDF가 열리고 50MB 합산 제한을 만족한다.
- 실제 시연 자료가 포함되어 있다.
- 외부 심사위원이 시크릿/로그인 없이 영상과 심사용 데모를 열 수 있다.
- 개인정보·고객정보·영업비밀·API 키가 없다.
- 생성형 AI, 외부 API, 오픈소스, 라이선스, 참고 아이디어를 고지한다.
- 저장소 공개 전 secret scan과 라이선스 검토를 완료한다.
- 모든 제출 파일의 SHA-256을 남기고 최종본을 동결한다.
- 최종 발표 참석 조건과 회사 이메일 인증을 포함한 신청 절차를 마감 1시간 전까지 끝낸다.

## 4. 발표자료의 최종 15장 구조

현재의 나선형 기억 성운과 진중한 VS Code 다크 테마는 유지하되, 전반부 설명을 압축하고 실증 근거의 비중을 높입니다.

1. **임팩트 오프닝** — 화면을 가득 채운 회전하는 나선형 기억 성운
2. **문제** — 이슈는 쌓이지만 처리 이유와 실패·롤백 맥락은 흩어진다
3. **히스토리의 정의** — 현재 상태를 만든 결정·변경·실패·의도의 연속
4. **근본 원인** — 정보가 아니라 관계 인덱스가 없어서 못 찾는다
5. **일반 검색 vs 그래프 검색** — 1-depth 키워드와 multi-hop 문맥 탐색의 차이
6. **Websidian의 AI 구조** — 근거 제한, 생성, 검증, 사람 승인, 폴백
7. **이슈 수명주기** — 생성/수집 → 탐색 → 처리 → 기억 생성 → 다음 이슈 재사용
8. **대표 3개 시나리오** — 롤백 재사용, 기획 의도, 타팀 파생 영향
9. **실제 시연** — WS-008 종단 흐름 또는 3분 영상 진입
10. **파일럿 방법** — 표본, 비교 과제, 측정식, 한계
11. **실제 업무 성과** — 시간·발견률·회귀조건·오판 수치
12. **AI 품질·자원 효율** — 검색 평가, 인용 정확도, 토큰·비용·지연, A/B
13. **신뢰·운영** — 권한, 마스킹, 승인, 정정, 감사, 비용·장애
14. **확장성** — GitHub는 예시; 비개발 사례와 전사 단계별 확장
15. **결론** — 과거 기록을 연결해 다음 판단 시간을 줄이는 조직 기억

온라인 발표는 15장으로 끝내고, PDF 뒤에는 발표하지 않는 검색 가능한 증거 부록을 붙입니다. 외부 40%·내부 40%·심사 AI 20% 구조를 고려해 핵심 숫자와 조건은 애니메이션이나 영상에만 두지 않고 PDF 텍스트로도 남깁니다.

### 4.1 15장 안에서 심사위원별로 가져가야 할 답

| 슬라이드 구간 | 일반·비기술 | 현업·경영 | 기술·AI 전문가 | AI 경험이 적은 숙련자 |
|---|---|---|---|---|
| 1~4 문제 | 왜 필요한지 | 반복 비용과 책임 문제 | 문제 정의의 경계 | 익숙한 이력 단절 문제 |
| 5~8 해결 | 검색보다 무엇이 나은지 | 실제 업무 흐름 | 검색·생성·검증 구조 | 원문·변경·승인·롤백 보존 |
| 9 시연 | 혼자 쓸 수 있는지 | 종단 업무가 되는지 | 실패·폴백이 있는지 | AI가 통제되는지 |
| 10~12 증거 | 좋아졌다는 큰 숫자 | 시간·품질·비용 | n·방법·정확도·토큰 | 기존 방식과 공정한 비교인지 |
| 13~14 운영 | 안심하고 쓸 수 있는지 | 도입·확장 가능성 | ACL·감사·성능 한계 | 책임과 정정 절차가 있는지 |
| 15 결론 | 한 문장 기억 | 투자할 이유 | 과장 없는 기여 | 기존 전문성을 증폭하는 도구 |

1. 현업 관련 참여자 5~10명 이상으로 확대
2. 합성 데이터 또는 사내 승인된 폐쇄 환경 데이터로 1~2주 반복 사용
3. 사용일수, 재사용률, 기억 재활용률, 중도 이탈, 반복 호출 비용 측정
4. 실제 운영 전 필요한 ACL·감사·마스킹·복구 기능을 시제품으로 보강
5. 본선 발표에는 예선의 1회성 통제 실험과 본선 전 반복사용 결과를 구분해서 제시

## 9. 현재 가장 큰 차단요소

코드·문서·영상·평가 자동화는 Codex가 만들 수 있지만, 다음 항목은 실제 사용자 행동이 필요합니다.

1. **합성 데이터 파일럿 참여자 3~5명 이상 확보**

   참여자가 없으면 정량적 성과 25점과 업무 적용 실효성 25점에서 “만점으로 판단할 실증”이 완성되지 않습니다.
2. **측정 참가자의 업무 관련성 확인**

   현업 동료가 참여하면 업무 판단 개선을 주장할 수 있고, 비현업 참여자라면 사용성 결과로 범위를 제한해야 합니다.

합성 데이터 전용 심사 링크와 전체 소스 공개는 사용자가 허용했습니다. 공개 실행 전에는 비밀정보·실데이터·라이선스 감사와 로그아웃 접근 검증을 완료해야 합니다.

현재 작업 트리에는 사용자 변경과 이전 ZIP이 남아 있으므로 지금 상태에서 공개 tag를 만들지 않습니다. 의도된 변경만 검토·커밋하고, 비밀정보 검사와 전체 테스트를 통과한 clean commit 하나에서 릴리스를 생성합니다. 기존 한글 파일명 ZIP은 버전 혼동과 호환성 위험 때문에 Release 자산으로 재사용하지 않습니다.

추가로 사용자에게 필요한 입력은 참가자/팀 정보, 회사 내 공개 가능한 직함·역할, 실제 파일럿 수치, 영상 공개 위치입니다. 그 밖의 구현·문서화·패키징·검증은 작업 범위로 묶을 수 있습니다.
