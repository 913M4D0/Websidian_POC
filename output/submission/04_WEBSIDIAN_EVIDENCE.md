### 3.2 정답셋과 순환 검증 방지

`ground-truth.json`은 대표 이슈의 원문·자료·처리 기록을 읽어 작성한 평가 전용 qrels다. 제품 검색 순위에 주입하지 않는다.

- 3등급: 핵심 판단 또는 핵심 위험을 직접 뒷받침
- 2등급: 조사 범위·대안 원인·운영 경계를 유의미하게 보강
- 1등급: 핵심 답은 아니지만 배제 여부를 확인할 가치가 있음
- 0등급: 해당 시나리오 판단에 사용할 구체적 연결이 없음

각 시나리오에는 7개의 관련 이력, 기대 직접 이력과 기대 2-hop 경로가 별도로 고정돼 있다. 특히 `WS-006`의 허용 경로는 제품이 실제 선택한 경로가 아니라 원문상 더 강한 `WS-005 → WS-006`으로 사전에 기록됐다. 따라서 현재 출력에 맞춰 정답을 복사한 평가가 아니다.

## 7. 생산성 대리지표의 의미

첫 3등급 근거까지 필요한 문서 수는 세 방법 모두 평균 `1.33건`이었다. 즉 Websidian이 첫 번째 그럴듯한 기록을 더 빨리 보여줬다는 증거는 없다. 관측된 이점은 여러 이슈에 흩어진 핵심 근거를 Top-10 안에 빠짐없이 모으고 비관련 결과를 줄이는 단계에 있다.

발표에서 사용할 수 있는 문장은 다음 범위다.

> 합성 시나리오 3건에서 Websidian 2-hop은 모든 핵심 근거가 나타나는 평균 순위를 17.00건에서 6.67건으로 낮췄습니다.

다음 문장은 현재 증거로 사용할 수 없다.

- 이슈 처리시간을 60.78% 단축했다.
- 실제 운영자의 조사시간을 10.33건만큼 줄였다.
- 장애나 사이드 이슈를 100% 예방한다.
- 키움증권 또는 계열사 전체의 생산성을 향상했다.

이를 검증하려면 실제 참여자가 기존 방식과 Websidian을 교차 순서로 사용하고, 첫 유효근거 발견시간·처리방향 확정시간·핵심근거 발견률·테스트 조건 누락을 별도로 측정해야 한다.

### 7.1 테스트 케이스의 실무 가치 가설과 다음 측정

현재 구현은 연결된 완료 이력에서 정상 흐름뿐 아니라 과거 재시도, 롤백, 날짜·상태 경계, 타팀 변경과 회귀 조건을 테스트 초안으로 제안한다. 개발자가 자신이 구현한 정상 경로를 가장 잘 아는 반면, 변경이 닿는 다른 화면·공통 모듈·과거 장애 조건은 놓치기 쉽다는 문제를 보완하려는 기능이다.

다만 이번 자체 벤치마크는 검색 근거의 순위와 밀도를 평가했을 뿐, 생성된 테스트의 결함 검출력은 평가하지 않았다. 제한 파일럿에서는 정답이 있는 사이드 결함 과제를 두고 `핵심 조건 회수율`, `기존 수동 케이스 대비 추가 유효 조건 수`, `중복·오탐 비율`, `검토·수정 시간`, `배포 후 회귀 결함`을 분리 측정해야 한다. 따라서 현재 안전한 주장은 `과거 사이드 이력을 테스트 후보로 전환하는 워크플로를 구현했다`까지다.

## 8. AI 문맥 효율 대리 측정

제품의 `buildIssueInsightContext`가 각 기준 이슈에서 실제로 선택한 문맥과, 동일한 필드·발췌 길이로 완료 이력 251건 전체를 투영한 비교 문맥을 직렬화해 비교했다. 비교 문맥은 모델에 전송하지 않았고 비용도 발생시키지 않았다.

| 기준 이슈 | 선택 이력 | 전체 완료 이력 |          선택 문맥 |         전체 비교 문맥 | 문자수 비율 |
| --------- | --------: | -------------: | -----------------: | ---------------------: | ----------: |
| WS-008    |       7건 |          251건 |            6,468자 |              173,650자 |       3.72% |
| WS-016    |       7건 |          251건 |            6,102자 |              173,649자 |       3.51% |
| WS-024    |       7건 |          251건 |            6,146자 |              173,669자 |       3.54% |
| 평균      |       7건 |          251건 | 범위 6,102~6,468자 | 범위 173,649~173,669자 |   **3.59%** |

건수 기준으로는 `7/251`, 즉 `2.79%`의 완료 이력만 선택됐다. 평균 문자수 비율은 3.59%로 전체 비교 문맥보다 96.41% 작았다. 전체 비교 문맥은 세 과제 모두 현재 64KB 입력 제한을 초과했다.

문자수는 토큰이 아니고, 문자수 비율은 비용 비율이 아니다. 시스템 프롬프트와 모델별 토크나이저, 추론 토큰, 캐시, 제공자 가격이 포함되지 않았기 때문이다. 따라서 현재 안전한 결론은 `관련 완료 이력 후보와 직렬화 문맥을 제한했다`까지다.

## 9. AI 텔레메트리

### 9.1 구현된 측정 항목

분석, 테스트 케이스, 파생 기억, 문서 임베딩과 쿼리 임베딩 호출에는 다음 메타데이터를 기록할 수 있다.

- 요청·제공 모델 ID와 프롬프트 버전
- 추론 강도, 근거 수와 입력 문자수
- 시작·완료시각, 첫 출력 시간(TTFT)과 총시간
- 입력·출력·추론·캐시·전체 토큰
- OpenRouter가 반환한 경우의 비용
- 제공자 요청 ID, 시도 횟수, 종료 사유
- 성공·부분·폴백·취소·오류 상태와 오류 단계

측정 테이블에는 프롬프트, 이슈 원문, 생성 결과, API 키와 이메일을 저장하지 않는다. 인증 소유자 값은 일방향 SHA-256 범위값으로 저장하며, 현재 사용자의 행만 `/api/metrics/llm?format=csv`로 내보낼 수 있다.

### 9.2 현재 증거 상태

이번 검색 벤치마크는 유료 LLM 생성이나 임베딩 호출을 수행하지 않았다. 따라서 이 보고서에는 실제 모델 ID, TTFT, 총 생성시간, 토큰, 제공자 비용, 재시도율 또는 폴백률의 관측값이 없다. 텔레메트리 **구현**과 AI 자원 **실측 결과**를 같은 것으로 취급하지 않는다.

OpenRouter 비용은 응답에 값이 있을 때만 `openrouter-credit`의 백만분율 정수로 저장한다. 임베딩 응답이 비용을 주지 않으면 빈 값을 0원으로 해석하거나 전체 AI 비용으로 합산해서는 안 된다. 제출 전에 실제 호출을 근거로 사용할 경우 OpenRouter 사용 내역과 CSV를 대조해야 한다.

## 10. 서버 함수 실행시간

| 방법            |       p50 |       p95 |
| --------------- | --------: | --------: |
| 텍스트 기준선   | 13.0347ms | 14.4240ms |
| Websidian 검색  | 16.0464ms | 17.8971ms |
| Websidian 2-hop | 38.5890ms | 42.9335ms |

2-hop은 기준선보다 로컬 서버 함수 시간이 길었다. 품질 개선과 함께 이 계산비용을 숨기지 않는다. 다만 이 수치는 데이터 로딩, 네트워크, 브라우저, AI 생성과 사람이 읽는 시간을 제외하므로 실제 화면 응답시간으로 사용할 수 없다. 다른 장비와의 절대 비교에도 적합하지 않다.

## 11. 숨기지 않은 실패 1건

`WS-008`의 기대 2-hop 경로 두 개 중 `WS-002`는 허용된 `WS-007 → WS-002` 경로로 찾았다. `WS-006`도 depth 2에서 회수했지만, 사전에 고정한 더 강한 `WS-005 → WS-006`이 아니라 `WS-007 → WS-006`으로 제시했다.

- 2-hop 목표 회수: 성공
- 엄격한 경로 회수: 실패
- WS-008 엄격 경로 회수율: `1/2`, 50.00%
- 전체 엄격 경로 회수율: `5/6`, 83.33%

이 실패는 목표 노드를 찾는 것과 설명 가능한 경유 경로를 고르는 것이 다른 문제임을 보여준다. 정답셋을 결과에 맞춰 수정하지 않았다. 후속 개선 후보는 공유 자료의 종류와 처리 이력 근거를 경로 선택 점수에서 분리하고, 동일 target의 복수 경로를 사용자에게 보여주는 것이다. 개선 후에는 같은 고정 qrels로 재측정해야 한다.

8. 실행 환경과 순간 부하는 함수 시간에 영향을 준다. 절대시간이나 사용자 체감시간이 아니라 동일 실행 안의 상대 결과로만 해석한다.
