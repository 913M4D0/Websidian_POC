# Websidian · 독립형 Issue Memory

웹에서 이슈를 만들고 처리하며, 완료된 기록을 다음 업무의 히스토리로 재사용하는 POC.
GitHub는 선택적인 외부 연결 예시일 뿐이며, 이슈 생성·탐색·처리에 GitHub 계정이나 저장소가 필요하지 않다.

## 제품 흐름

1. **신규 이슈 생성**: 원문, 발생일, 담당 팀, 자유 분류·태그·속성, 관련 자료를 저장한다.
2. **신규 이슈 확인과 히스토리 탐색**: 진행 중 이슈를 선택하면 임시 작업 노드가 완료 기억들과 연결된다. 검색·2-hop 근거 탐색·원문 조회·진행 기록 추가를 지원한다.
3. **처리 완료**: 처리 내용·결과·추가 자료·참고한 완료 이슈를 기록한다. 원문 제목·본문·기존 자료를 덮어쓰지 않는다.
4. **기억 전환**: 임시 작업 노드를 없애고 완료 기억 노드를 표시한다. 원문 용어와 참고 이슈 ID를 별도 메타데이터로 저장한다.
5. **다음 이슈에서 재사용**: 새로 완료된 이슈가 검색·히스토리·기억 그래프에 포함된다.

화면의 노드 ID는 `active:<issueId>` → `memory:<issueId>`로 바뀌지만, 저장된 이슈의 canonical ID는 유지된다.
즉 임시 **표현**을 교체하는 것이지 원본 이슈를 삭제하거나 동일 사건을 두 번 저장하는 것이 아니다.
Brief나 조회 결과는 이슈 노드가 아니며, 검색 때문에 이슈 제목·본문이 바뀌지 않는다.

## 현재 데이터와 구현 범위

- 합성 이슈 **294건**: 대표 24건 + 일반 270건. 실제 회사 사건·자료가 아니다.
- 초기 기억 유니버스는 **완료 251건**, 진행 중 작업 목록은 **43건**이다. 선택한 진행 이슈 하나만 임시 노드로 더해진다.
- 대표 24건은 과거 완료 21건 + 신규 미해결 3건, 일반 270건은 완료 230건 + 미해결 40건이다.
- 원문 조회, 자유 필드 입력, 생성, 진행 기록, 완료 처리 및 사용자별 D1 영구 저장을 구현했다.
- seed와 사용자별 수정·생성 overlay를 동일 ID로 합친다. 재배포해도 저장된 처리 기록을 seed로 초기화하지 않는다.
- 생성 요청은 멱등성을 갖고, 진행·완료 변경은 revision CAS로 동시 충돌을 거부한다.
- VS Code 다크 테마, 살아 움직이는 3D 성운, 드래그·포인터 반응, 중력 트리, 밝기 강조·관계선 밀도 조절을 제공한다.
- 원문 기반 자동 히스토리 수집은 동작한다. **현재 LLM 서버 설정이 없으므로 실제 AI 호출은 하지 않는다.**

## 검색·히스토리·기억의 구분

| 기능            | 현재 방법                                                                                | 하지 않는 것                              |
| --------------- | ---------------------------------------------------------------------------------------- | ----------------------------------------- |
| 완료 이슈 검색  | 한국어 단어·bigram cosine/IDF, 공통 자료 식별자                                          | 의미 임베딩 검색 또는 LLM 관련도 판정     |
| 히스토리 수집   | 직접 검색 상위 8건 + 고정 근거, 각 이슈의 상위 4개 관계 및 명시적 참고 연결을 2-hop 탐색 | 시나리오 정답 경로 주입, 인과관계 확정    |
| 히스토리 발췌   | 완료 처리 본문 등 원문의 일부를 그대로 제공                                              | 질문에 맞춘 원문 재작성·AI 요약           |
| 완료 기억 생성  | `extractive-v1`: 용어 추출과 참고 이슈 ID 저장                                           | LLM 컴파일·자동 분류·자동 평가            |
| 선택적 AI Brief | 서버가 수집한 완료 근거를 OpenRouter에 전달, 인용 ID와 결과 형식 검증                    | 원문 수정, 자동 이슈 처리, 외부 도구 실행 |

완료 기억 메타데이터는 `memory: {version, compiledAt, method, sourceRevision, terms, relatedIssueIds}`이며 원문과 분리되어 있다.
기존 완료 seed는 메타데이터를 소급 생성하거나 원문을 고치지 않아도 기억으로 취급한다.
처리 시 고정한 근거는 `resolution.evidenceIssueIds`에도 남으며 실제 접근 가능한 완료 이슈만 허용한다.

검색 결과는 **완료 이슈 전체**를 순위순으로 반환하고 UI가 페이지를 나눈다.
진행 중 기준 이슈는 자료 일치 계산에는 사용하지만 과거 해결 근거로 반환하지 않는다.
분류·팀 일치는 필수 조건이 아니며, 무일치 검색은 히스토리 근거가 없는 상태로 표시한다.

## 탐색·배치 v1

- 검색 점수: 텍스트 일치 80% + 자료 일치 20%.
- 그래프 점수: 텍스트 일치 75% + 동일 자료 Jaccard 25%.
- 날짜 차이는 독립 정보이며 성운 초기 위치를 보조한다. 시간상 가깝다는 이유로 원인으로 판단하지 않는다.
- 기본 노드당 상위 4개 연결의 합집합을 표시한다. 1~10 조절은 화면 밀도 예산이지 검색 후보 제외 기준이 아니다.
- 처리 시 명시적으로 참고한 기억의 연결은 이 표시 예산과 관계없이 남는다. 점수를 인위적으로 높이지 않는다.
- 명시적 참고 연결은 자동 히스토리 탐색에서도 양방향으로 따라간다. 유사도 0이어도 기록된 연결을 유지하지만, 없는 이슈·자기 자신·접근 불가·미완료 대상은 제외한다.
- 진행 중 이슈를 선택해도 기존 완료 기억 사이 연결을 대체하지 않는다.
- 연결 후보는 데이터 버전별로 캐시한다. 관계선 조절은 포인터·키 조작 완료 시 반영한다.
- 트리는 최대 3-hop, 레벨별 64/44/36건을 표시하고 나머지는 배경에 남긴다. 이는 시각화 한도이며 모든 이슈는 목록에서 확인할 수 있다.
- 색상은 담당 팀을 나타내며 선택은 밝기로 강조한다. 임시 작업 노드만 호박색으로 구분한다.
- 트리의 위아래는 탐색 깊이지 시간 순서·인과관계가 아니다. 2-hop 근거의 공통 자료·날짜 차이는 바로 앞 경유 이슈와 비교한 값이다.

## API

모든 API는 로그인한 사용자의 작업공간에 한정된다. POST는 같은 origin의 JSON 요청만 허용한다.

| 경로                              | 역할                                                              |
| --------------------------------- | ----------------------------------------------------------------- |
| `GET /api/issues`                 | 사용자 데이터와 seed를 합쳐 반환                                  |
| `POST /api/issues`                | `requestId`를 이용한 멱등 신규 생성                               |
| `POST /api/issues/:id/activities` | `expectedRevision, body`로 진행 기록 추가                         |
| `POST /api/issues/:id/resolve`    | `expectedRevision, body, outcome` 및 선택적 자료·참고 이슈로 완료 |
| `POST /api/search`                | `query, excludeId?`로 완료 기억 검색                              |
| `POST /api/history`               | `query, referenceId?, pinnedIds?`로 원문 기반 2-hop 근거 수집     |
| `GET /api/llm`                    | 서버 AI 연결 준비 상태 확인                                       |
| `POST /api/brief`                 | `query, referenceId?, pinnedIds?`로 선택적 AI Brief 요청          |

완료 요청의 `resources`는 기존 자료 식별자를 덮어쓰지 않고 새 자료만 추가한다.
`evidenceIssueIds`는 해당 사용자가 접근 가능한 완료 이슈만 허용한다.
완료된 이슈에 진행 기록을 추가하거나 중복 완료하는 요청과 stale revision은 409로 거부한다.

## 선택적 OpenRouter Brief

서버 어댑터는 구현되어 있으나 **현재 비밀 설정이 없어 미연결 상태**이다.
`GET /api/llm`의 `ready`가 실제 준비 상태이며, 정적 `llmPolicy.enabled` 값은 런타임 연결 상태가 아니다.
미설정 시 `POST /api/brief`는 503을 반환하고 원문이나 처리 상태를 바꾸지 않는다.

서버에만 다음 값을 설정한다. 키를 소스·브라우저·채팅에 붙여 넣지 않는다.

| 서버 설정            | 값                                           |
| -------------------- | -------------------------------------------- |
| `OPENROUTER_API_KEY` | 관리자가 준비한 서버 전용 OpenRouter 비밀 키 |
| `OPENROUTER_MODEL`   | `openai/gpt-5.6-luna`                        |

모델 ID는 2026-09-04 [OpenRouter 공식 모델 목록](https://openrouter.ai/api/v1/models)에서 확인했으며 런타임에도 재확인한다.
지원된 추론 강도 중 가장 높은 값을 선택한다. 현재 확인된 최대값은 `max`다.
모델별 지원값을 확인하는 방법과 `reasoning.effort`의 의미는 [공식 추론 문서](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens)를 따른다.
다른 모델·별도 Pro 모델로 자동 대체하지 않는다.

- 접근 가능한 완료 이슈에서 서버가 근거를 다시 구성한다. 클라이언트가 보내는 임의 원문·모델·프롬프트를 사용하지 않는다.
- 제공 이슈만 인용하도록 구조화 출력을 요구하고, 사실/추정을 구분한다. 인용 ID 검증이 내용의 진실성까지 보장하는 것은 아니다.
- 원문과 질문은 비신뢰 자료로 취급하며 내부 지시를 실행하거나 도구를 호출하지 않는다.
- 근거는 최대 16건의 발췌문이며 고정한 근거를 우선한다. 조회한 모든 기록이 모델에 전달되는 것은 아니다.
- 임의 업무 분류 게이트·추가 내용 필터는 두지 않는다. 개인정보·접근 권한·제공자의 필수 정책은 유지한다.
- 비용 보호를 위해 추론을 포함한 출력 상한 16,000토큰, 요청 45초, 사용자당 1분 2회·1시간 12회 제한이 있다. 모델이 공지한 출력 한도가 더 낮으면 그 한도를 따른다.
- 모델·키 설정을 확인해도 키 권한·잔액 및 실제 생성 품질은 유료 요청 전에는 검증되지 않는다.
- 현재까지 실제 유료 LLM 생성 호출은 하지 않았다.

## GitHub는 선택적인 연동 예시

[대표 GitHub 이슈 24건](https://github.com/913M4D0/Websidian_POC/issues?q=is%3Aissue)은 2026-09-04 등록한 합성 예시다.
등록 당시 과거 21건은 closed, 신규 3건은 open으로 두었으며 일반 270건은 외부에 등록하지 않았다.
검증한 실제 번호·URL을 `data/github-bindings.json`에 기록해 원본 링크로 제공한다.

현재 연결은 **정적 외부 참조**다. 자동 가져오기, 댓글·PR·커밋 수집, 웹훅, 양방향 동기화는 구현하지 않았다.
웹에서 처리 완료해도 GitHub 이슈 상태를 변경하지 않는다.
GitHub 없이 모든 핵심 이슈 처리 기능을 사용할 수 있으며, 향후 다른 형상관리·업무 플랫폼도 같은 외부 참조 구조로 연결할 수 있다.

## 실행 / 검증

```sh
npm ci
npm run dev
# http://localhost:3000/signin-with-chatgpt?return_to=/ 로 로컬 시뮬레이션 로그인
npm run test
npx tsc --noEmit
npx oxlint components/memory-universe.tsx components/issue-graph.tsx lib app/api tests scripts/smoke-local.mjs
node scripts/smoke-local.mjs
npm run build
```

Sites의 로그인은 POC 작업공간 접근용이며 GitHub 인증이 아니다.
`smoke-local.mjs`는 localhost:3000 전용이며 유료 AI가 준비되지 않은 상태에서만 실행한다.
자신이 만든 QA 이슈 한 건으로 생성·진행·완료·동시 충돌·기억 전환·검색·히스토리·미설정 AI 응답을 검증하고,
해당 실행의 정확한 QA 행만 삭제한다. 기존 294건과 사용자가 만든 다른 이슈는 삭제하지 않는다.

단위 테스트는 원문 불변성, 자유 분류, 동시 변경 계약, 완료 그래프 전환, 2-hop 탐색, AI 요청·인용 검증을 다룬다.
로컬 API smoke에서 신규 생성 r1 → 진행 기록 r2 → 완료 기억 r3, 동시 완료 [200, 409], 미설정 Brief 503,
인증 401·교차 출처 403·과대 입력 413 및 원본 데이터 보존을 확인했다.
별도 `scripts/browser-smoke.mjs`로 로컬 Headless Chrome에서 생성·진행 기록·히스토리·근거 선택·완료 전환·새로고침 후 유지와 모바일 탐색을 확인했다. 실행 오류 0건이며 테스트가 만든 UUID 이슈만 정리한다.
이 스크립트는 Playwright 패키지가 필요하다. 로컬에 없다면 `WEBSIDIAN_PLAYWRIGHT_PATH`에 사용 가능한 패키지의 절대 경로를 설정하고 `node scripts/browser-smoke.mjs`로 실행한다. `--inspect`는 데이터 생성 없이 탐색 화면을 검사한다.
유료 AI 생성 품질 및 로그인한 운영 환경의 처리 흐름은 이 로컬 검증으로 확인한 것으로 간주하지 않는다.
전체 `npm run lint`에는 기존 미사용 UI 프리미티브의 오류가 남아 있어 변경 파일 검사를 별도로 수행한다.

## 데이터와 코드 경계

| 계층                                            | 역할                                               |
| ----------------------------------------------- | -------------------------------------------------- |
| `data/issues.json`                              | 합성 원문·자료·처리 이력 294건                     |
| `data/github-issue-drafts.json`                 | 기존 GitHub 예시 등록 원문, 검색에는 사용하지 않음 |
| `data/github-bindings.json`                     | 선택적 외부 예시 ID/URL                            |
| `lib/issues.ts`                                 | 플랫폼 중립 계약, 원문 보존, 진행·완료·기억 추출   |
| `lib/issue-store.ts`                            | 사용자별 D1 저장, 생성 멱등성, revision CAS        |
| `lib/issue-search.ts` / `lib/issue-history.ts`  | 검색·다단계 근거 수집, 원문과 분석 상태 분리       |
| `lib/memory-graph.ts` / `lib/gravity-layout.ts` | 임시 작업/완료 기억 표현과 탐색 배치               |
| `lib/brief-contract.ts` / `lib/llm-server.ts`   | 서버 전용 AI 요청·출력 검증과 사용 제한            |
| `lib/llm-policy.ts`                             | 비밀이 없는 모델 선택 정책                         |

분류·평가 항목은 자유 문자열 키/값이다. 개별 입력 길이·개수 제한은 자원 보호용이며 고정 업무 분류 체계가 아니다.
관련 자료는 코드·문서·정책·양식·프로세스 모두 가능하다. seed의 `code:/`, `doc:/` 등은 합성 식별자이며 실제 파일·커밋 증거가 아니다.
발표용 정답 경로나 시나리오 재생 기능은 제품에 넣지 않았다.

대표 검증 사례는 과거 해결·롤백의 재사용(WS-008), 의도된 과거 소속 표시(WS-016), 타팀 시간대 변경의 사이드 탐색(WS-024)이다.
직접 검색에서 놓친 이슈도 실제 내용·자료의 다단계 연결로 탐색하도록 테스트하며, 답을 순위에 강제로 주입하지 않는다.

## 운영 경계와 남은 기능

Sites 게이트웨이가 주입·덮어쓰는 `oai-authenticated-user-id`를 신뢰하므로 별도 공개 Worker 주소로 우회 노출하면 안 된다.
DB 질의는 바인딩 파라미터와 사용자 ID 범위로 제한한다.
D1의 최초 스키마 생성은 인증 후 멱등적으로 실행하며, 향후 스키마 변경은 명시적 마이그레이션으로 전환해야 한다.

아직 구현하지 않은 범위:

- 의미 임베딩·벡터 검색, LLM 기억 컴파일·자동 분류·평가.
- GitHub 또는 다른 외부 플랫폼의 자동 수집·웹훅·양방향 동기화.
- 조직 공동 작업공간, 팀 공유 권한, 자료별 ACL, 운영용 감사·커넥터 비밀 관리.
- 완료 기억 재개방·정정 워크플로, 대량 데이터 성능 검증, 운영 백업·복구 체계.

현재는 **개인별 POC 작업공간**이다. 실제 전사 40~50명 공유 서비스와 동일한 권한·운영 체계라고 주장하지 않는다.
