# Websidian · 독립형 Issue Memory

웹에서 이슈를 만들고 처리하며, 완료된 기록을 다음 업무의 히스토리로 재사용하는 POC.
GitHub는 선택적인 외부 연결 예시일 뿐이며, 이슈 생성·탐색·처리에 GitHub 계정이나 저장소가 필요하지 않다.

> [!IMPORTANT]
> **공개 범위와 주장 경계**
>
> - 이 저장소는 개인이 구현한 **실무 유사 POC**다. 회사의 공식 제품, 승인된 운영 서비스 또는 전사 도입 사례가 아니다.
> - 기본 데이터는 대표 24건과 일반 270건으로 구성된 **합성 이슈 294건**이다. 실제 회사 이슈, 고객정보, 개인정보, 운영 코드·문서 또는 영업기밀을 재현한 자료가 아니다.
> - 데이터 건수·테스트 통과 수처럼 저장소에서 직접 확인되는 값은 구현 사실이다. 시간 절감률·정확도·비용 효과 등 별도의 정량값은 측정 조건과 표본을 명시한 POC 결과에만 적용되며, 실제 운영 성과나 회사 전체의 효과를 뜻하지 않는다.
> - 기획·구현·테스트·문서화에는 생성형 AI를 보조 도구로 사용했다. 실행 중 AI 기능은 사용자가 요청할 때만 OpenRouter를 통해 외부 모델을 호출하며, 결과의 채택과 업무 판단 책임은 사용자에게 있다.
> - 소스와 합성 데이터를 공개해 구조와 POC를 검토·재현할 수 있게 했지만, 현재 저장소에는 `LICENSE`가 없다. 권리 귀속과 제3자 구성요소의 조건을 확인하기 전까지 공개 열람을 별도의 사용·수정·재배포 허락으로 해석해서는 안 된다.
>
> 세부 고지: [합성 데이터](docs/SYNTHETIC_DATA_STATEMENT.md) · [AI 사용](docs/AI_USAGE_DISCLOSURE.md) · [보안과 개인정보](docs/SECURITY_AND_PRIVACY.md)

## 제품 흐름

1. **신규 이슈 생성**: 원문, 발생일, 담당 팀, 자유 분류·태그·속성, 관련 자료를 저장한다.
2. **신규 이슈 확인과 히스토리 탐색**: 목록이나 성운에서 이슈를 선택하면 관련 완료 기억이 최대 2단계로 자동 정렬된다. 연결된 노드를 하나씩 확인해도 처음 고른 분석 기준은 유지된다.
3. **처리 완료**: 처리 내용·결과·추가 자료·참고한 완료 이슈를 기록한다. 원문 제목·본문·기존 자료를 덮어쓰지 않는다.
4. **기억 전환**: 임시 작업 노드를 없애고 원문 기반 `extractive-v1` 완료 기억을 즉시 성운에 표시한다. 사용자가 요청하면 GPT 5.6 Luna가 원문 밖의 별도 파생 기억을 컴파일해 보강하며, 실패해도 완료 기억은 유지된다.
5. **다음 이슈에서 재사용**: 새로 완료된 이슈가 검색·히스토리·기억 그래프에 포함된다.

화면의 노드 ID는 `active:<issueId>` → `memory:<issueId>`로 바뀌지만, 저장된 이슈의 canonical ID는 유지된다.
즉 임시 **표현**을 교체하는 것이지 원본 이슈를 삭제하거나 동일 사건을 두 번 저장하는 것이 아니다.
AI 분석·테스트 결과나 조회 결과는 이슈 노드가 아니며, 검색 때문에 이슈 제목·본문이 바뀌지 않는다.

## 현재 데이터와 구현 범위

- 합성 이슈 **294건**: 대표 24건 + 일반 270건. 실제 회사 사건·자료가 아니다.
- 첫 화면의 이슈 성운에는 **전체 294건**이 모두 보인다. 완료 기억 251건은 담당 팀 색상, 진행 중 43건은 흰색 작업 노드로 구분한다.
- 대표 24건은 과거 완료 21건 + 신규 미해결 3건, 일반 270건은 완료 230건 + 미해결 40건이다.
- 원문 조회, 자유 필드 입력, 생성, 진행 기록, 완료 처리 및 사용자별 D1 영구 저장을 구현했다.
- seed와 사용자별 수정·생성 overlay를 동일 ID로 합친다. 재배포해도 저장된 처리 기록을 seed로 초기화하지 않는다.
- 생성 요청은 멱등성을 갖고, 진행·완료 변경은 revision CAS로 동시 충돌을 거부한다.
- VS Code 다크 테마, 시간 반경의 구형 5개 나선팔과 관계 기반 완화로 만든 성운, 느린 전체 공전과 미세한 상하 파동, 드래그·포인터 반응, 중력 트리, 밝기 강조·관계선 밀도 조절을 제공한다.
- 원문 기반 히스토리 수집, 선택적 GitHub 단방향 가져오기, GPT 5.6 Luna 기억 컴파일과 Qwen3 의미 색인을 구현했다. 외부 호출은 사용자가 실행할 때만 발생한다.
- 처음 선택한 이슈 기준의 `이 이슈 분석`과 `테스트 케이스` 버튼이 관련 이력을 서버에서 자동 수집한다. 핀이나 근거 담기 단계는 필요하지 않다.
- WS-008은 시연용 완료 내용·결과·자료가 미리 입력돼 있으며, 완료 처리 직후 원문 기반 기억 노드가 별처럼 탄생한다. 선택적 Luna 파생 기억은 이후 별도 생성·검증한다.

## 검색·히스토리·기억의 구분

| 기능           | 현재 방법                                                                                | 하지 않는 것                              |
| -------------- | ---------------------------------------------------------------------------------------- | ----------------------------------------- |
| 완료 이슈 검색 | 기본은 한국어 단어·bigram/IDF+자료, 색인 후 의미 55%·문장 30%·자료 15% 혼합              | 의미 점수를 정답·인과 확률로 해석         |
| 히스토리 수집  | 기준 이슈 직접 검색 상위 5건, 각 이슈의 상위 4개 관계 및 명시적 참고 연결을 2-hop 탐색   | 시나리오 정답 경로 주입, 인과관계 확정    |
| 히스토리 발췌  | 완료 처리 본문 등 원문의 일부를 그대로 제공                                              | 질문에 맞춘 원문 재작성·AI 요약           |
| 완료 기억 생성 | 완료는 즉시 `extractive-v1`, 별도 파생 저장소에 Luna 요약·자유 facet·임베딩을 선택 생성  | 원문 제목·본문·처리 이력 재작성           |
| AI 분석·테스트 | 처음 고른 이슈의 관련 이력을 서버가 자동 수집하고, OpenRouter 응답의 형식·인용 ID를 검증 | 원문 수정, 자동 이슈 처리, 외부 도구 실행 |

완료 기억 메타데이터는 `memory: {version, compiledAt, method, sourceRevision, terms, relatedIssueIds}`이며 원문과 분리되어 있다.
LLM 결과와 벡터는 `websidian_memory_artifacts`에 별도로 저장하며 벡터·요약은 브라우저로 보내지 않는다. 노드는 끝까지 이슈이며 AI 해석은 분석·테스트 결과 화면에서만 표시한다.
기존 완료 seed는 메타데이터를 소급 생성하거나 원문을 고치지 않아도 기억으로 취급한다.
처리 시 고정한 근거는 `resolution.evidenceIssueIds`에도 남으며 실제 접근 가능한 완료 이슈만 허용한다.

검색 결과는 **완료 이슈 전체**를 순위순으로 반환하고 UI가 페이지를 나눈다.
진행 중 기준 이슈는 자료 일치 계산에는 사용하지만 과거 해결 근거로 반환하지 않는다.
분류·팀 일치는 필수 조건이 아니며, 무일치 검색은 히스토리 근거가 없는 상태로 표시한다.

## 탐색·배치 v1

- 검색 점수: 텍스트 일치 80% + 자료 일치 20%.
- 그래프 점수: 텍스트 일치 75% + 동일 자료 Jaccard 25%.
- 같은 모델의 의미 색인이 있으면 검색·의미 연결은 임베딩 55% + 텍스트 30% + 자료 15%로 계산한다. 색인이 없거나 제공자 호출이 실패하면 기존 원문 검색으로 안전하게 돌아간다.
- 날짜 차이는 독립 정보이며 성운 초기 위치를 보조한다. 시간상 가깝다는 이유로 원인으로 판단하지 않는다.
- 화면 기본값은 노드당 상위 5개 연결의 합집합이다. 1~10 조절은 화면 밀도 예산이지 검색 후보 제외 기준이 아니다.
- 처리 시 명시적으로 참고한 기억의 연결은 이 표시 예산과 관계없이 남는다. 점수를 인위적으로 높이지 않는다.
- 명시적 참고 연결은 자동 히스토리 탐색에서도 양방향으로 따라간다. 유사도 0이어도 기록된 연결을 유지하지만, 없는 이슈·자기 자신·접근 불가·미완료 대상은 제외한다.
- 모든 진행 중 이슈도 첫 화면부터 표시되며 완료 기억과의 실제 상위 연결을 함께 보여준다. 진행 이슈를 선택해도 기존 완료 기억 사이 연결을 대체하지 않는다.
- 연결 후보는 데이터 버전별로 캐시한다. 관계선 조절은 포인터·키 조작 완료 시 반영한다.
- 트리는 최대 3-hop, 레벨별 12/18/24건을 표시하고 나머지는 배경에 남긴다. 이는 가독성을 위한 시각화 한도이며 모든 이슈는 목록에서 확인할 수 있다.
- 색상은 담당 팀을 나타내며 선택은 밝기와 외곽 링으로 강조한다. 임시 작업 노드만 흰색으로 구분한다.
- 트리의 위아래는 탐색 깊이지 시간 순서·인과관계가 아니다. 2-hop 근거의 공통 자료·날짜 차이는 바로 앞 경유 이슈와 비교한 값이다.

## API

모든 API는 로그인한 사용자의 작업공간에 한정된다. POST는 같은 origin의 JSON 요청만 허용한다.

| 경로                                   | 역할                                                                               |
| -------------------------------------- | ---------------------------------------------------------------------------------- |
| `GET /api/issues`                      | 사용자 데이터와 seed를 합쳐 반환                                                   |
| `POST /api/issues`                     | `requestId`를 이용한 멱등 신규 생성                                                |
| `POST /api/issues/:id/activities`      | `expectedRevision, body`로 진행 기록 추가                                          |
| `POST /api/issues/:id/resolve`         | `expectedRevision, body, outcome` 및 선택적 자료로 완료, 관련 근거는 서버가 재수집 |
| `POST /api/search`                     | `query, excludeId?`로 완료 기억 검색                                               |
| `POST /api/history`                    | `query, referenceId?, pinnedIds?`로 원문 기반 2-hop 근거 수집                      |
| `GET /api/llm`                         | 서버 AI 연결 준비 상태 확인                                                        |
| `POST /api/issues/:id/analyze`         | 해당 이슈 기준 관련 이력을 자동 수집해 인용 가능한 분석 생성                       |
| `POST /api/issues/:id/test-cases`      | 동일한 관련 이력으로 인용 가능한 테스트 케이스 생성                                |
| `GET/POST /api/memory/index`           | 의미 색인 상태 조회 / 완료 기억을 최대 32건씩 사용자 실행 색인                     |
| `POST /api/issues/:id/memory/compile`  | 완료 이슈의 Luna 파생 기억·임베딩을 멱등 생성                                      |
| `POST /api/integrations/github/import` | 공개/권한 있는 GitHub 이슈·댓글을 단방향 스냅샷으로 가져오기                       |
| `GET /api/metrics/llm`                 | 현재 사용자 범위의 내용 없는 AI 측정 로그 조회, `?format=csv`로 CSV 내보내기        |

완료 요청의 `resources`는 기존 자료 식별자를 덮어쓰지 않고 새 자료만 추가한다.
`evidenceIssueIds`는 해당 사용자가 접근 가능한 완료 이슈만 허용한다.
완료된 이슈에 진행 기록을 추가하거나 중복 완료하는 요청과 stale revision은 409로 거부한다.

## 선택적 OpenRouter 분석·테스트·Memory

서버 어댑터는 구현되어 있으며 준비 여부는 런타임 설정과 OpenRouter 공개 모델 목록으로 확인한다.
`GET /api/llm`의 `ready`가 실제 준비 상태이며, 정적 `llmPolicy.enabled` 값은 런타임 연결 상태가 아니다.
미설정 또는 제공자 장애 시 분석·테스트·기억 생성은 원문 기반 안전 결과로 대체되며 원문이나 처리 상태를 바꾸지 않는다.

서버에만 다음 값을 설정한다. 키를 소스·브라우저·채팅에 붙여 넣지 않는다.

| 서버 설정                    | 값                                           |
| ---------------------------- | -------------------------------------------- |
| `OPENROUTER_API_KEY`         | 관리자가 준비한 서버 전용 OpenRouter 비밀 키 |
| `OPENROUTER_MODEL`           | `openai/gpt-5.6-luna`                        |
| `OPENROUTER_EMBEDDING_MODEL` | `qwen/qwen3-embedding-8b`                    |

모델 ID는 2026-09-04 [OpenRouter 공식 모델 목록](https://openrouter.ai/api/v1/models)에서 확인했으며 런타임에도 재확인한다.
지원 여부를 런타임에 확인한 뒤 `max` 추론을 사용하며, `max`를 확인할 수 없으면 더 낮은 강도로 묵시적 대체하지 않는다.
모델별 지원값을 확인하는 방법과 `reasoning.effort`의 의미는 [공식 추론 문서](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens)를 따른다.
다른 모델·별도 Pro 모델로 자동 대체하지 않는다.

- 접근 가능한 완료 이슈에서 서버가 근거를 다시 구성한다. 클라이언트가 보내는 임의 원문·모델·프롬프트를 사용하지 않는다.
- 제공 이슈만 인용하도록 구조화 출력을 요구하고, 사실/추정을 구분한다. 인용 ID 검증이 내용의 진실성까지 보장하는 것은 아니다.
- 원문과 질문은 비신뢰 자료로 취급하며 내부 지시를 실행하거나 도구를 호출하지 않는다.
- 근거는 서버가 자동 수집한 접근 가능한 완료 이슈의 발췌문이며, 조회한 모든 기록이 모델에 전달되는 것은 아니다.
- 임의 업무 분류 게이트·추가 내용 필터는 두지 않는다. 개인정보·접근 권한·제공자의 필수 정책은 유지한다.
- 최대 추론 요청을 유지하되 비정상적 무한 생성은 막기 위해 분석·테스트 케이스·파생 기억 모두 출력 16,000토큰·180초 상한을 둔다. 사용자별 호출 제한은 전체 1분 12회·1시간 120회이며, 같은 기능은 1분 6회·1시간 60회다. 실패한 외부 호출도 예약된 한도를 사용하며, 모델이 공지한 출력 한도가 더 낮으면 그 한도를 따른다.
- 모델·키 설정을 확인해도 키 권한·잔액 및 실제 생성 품질은 유료 요청 전에는 검증되지 않는다.
- 자동 검증은 유료 LLM 생성을 호출하지 않으며, 실제 생성은 사용자가 분석·테스트·기억 생성 기능을 실행할 때만 요청한다.
- 의미 색인은 32건 단위의 명시적 버튼으로만 실행한다. `data_collection: deny`, `zdr: true`를 요청하고 같은 임베딩 모델·차원만 비교한다. 모델 변경 시 전체 재색인이 필요하다.

## GitHub는 선택적인 연동 예시

[대표 GitHub 이슈 24건](https://github.com/913M4D0/Websidian_POC/issues?q=is%3Aissue)은 2026-09-04 등록한 합성 예시다.
등록 당시 과거 21건은 closed, 신규 3건은 open으로 두었으며 일반 270건은 외부에 등록하지 않았다.
검증한 실제 번호·URL을 `data/github-bindings.json`에 기록해 원본 링크로 제공한다.

기존 24건의 정적 외부 참조와 함께 **사용자 실행 단방향 스냅샷 가져오기**를 제공한다. GitHub REST 이슈·댓글을 최대 이슈 300건까지 읽고 PR은 제외한다. 재실행은 기존 Websidian 처리 내용을 덮어쓰지 않는다.
공개 저장소는 토큰 없이 가능하고, 비공개 저장소는 서버 전용 `GITHUB_TOKEN`이 선택 사항이다. 토큰은 브라우저 입력이나 응답에 포함하지 않는다.
웹에서 처리 완료해도 GitHub 이슈 상태를 변경하지 않는다.
GitHub 없이 모든 핵심 이슈 처리 기능을 사용할 수 있으며, 향후 다른 형상관리·업무 플랫폼도 같은 외부 참조 구조로 연결할 수 있다.

### 합성 자체 벤치마크

실제 증권 운영 이슈는 보안상 사용하지 않습니다. 대신 대표 24건과 배경 270건의 완전 합성 데이터에서 텍스트 기준선과 현재 제품 검색·2-hop 탐색을 같은 정답셋으로 비교합니다.

```powershell
node --experimental-strip-types scripts/eval-retrieval.mjs `
  --iterations 100 `
  --output-dir evidence/poc-benchmark/results
```

측정 방법과 주장 범위는 [프로토콜](evidence/poc-benchmark/protocol.md), 채점식은 [채점 기준](evidence/poc-benchmark/scoring-rubric.md), 현재 결과와 실패 항목은 [결과 요약](evidence/poc-benchmark/results-summary.md)에 공개합니다. 문서 확인 수·근거 밀도·컨텍스트 문자수는 생산성 **대리지표**이며 실제 사용자 시간·비용 절감률로 환산하지 않습니다.

Sites의 로그인은 POC 작업공간 접근용이며 GitHub 인증이 아니다.
`smoke-local.mjs`는 localhost:3000 전용이며 유료 AI가 준비되지 않은 상태에서만 실행한다.
자신이 만든 QA 이슈 한 건으로 생성·진행·완료·동시 충돌·기억 전환·검색·히스토리를 검증하고,
해당 실행의 정확한 QA 행만 삭제한다. 기존 294건과 사용자가 만든 다른 이슈는 삭제하지 않는다.

단위 테스트는 원문 불변성, 자유 분류, 동시 변경 계약, 전체 294개 그래프와 규칙적 성운, 완료 그래프 전환, 대표 3개 시나리오의 2-hop 탐색, AI 분석·테스트 요청과 인용 검증, GitHub URL/상태 보존, 임베딩 차원 격리와 혼합 순위를 다룬다.
로컬 API smoke에서 신규 생성 r1 → 진행 기록 r2 → 완료 기억 r3, 동시 완료 [200, 409],
인증 401·교차 출처 403·과대 입력 413 및 원본 데이터 보존을 확인했다.
별도 `scripts/browser-smoke.mjs`로 로컬 Headless Chrome에서 생성·진행 기록·관련 이슈·완료 전환·새로고침 후 유지와 모바일 탐색을 확인한다. 테스트가 만든 UUID 이슈만 정리한다.
이 스크립트는 Playwright 패키지가 필요하다. 로컬에 없다면 `WEBSIDIAN_PLAYWRIGHT_PATH`에 사용 가능한 패키지의 절대 경로를 설정하고 `node scripts/browser-smoke.mjs`로 실행한다. `--inspect`는 데이터 생성 없이 탐색 화면을 검사한다.
유료 AI 생성 품질 및 로그인한 운영 환경의 처리 흐름은 이 로컬 검증으로 확인한 것으로 간주하지 않는다.
전체 `npm run lint`에는 기존 미사용 UI 프리미티브의 오류가 남아 있어 변경 파일 검사를 별도로 수행한다.

## 데이터와 코드 경계

| 계층                                               | 역할                                               |
| -------------------------------------------------- | -------------------------------------------------- |
| `data/issues.json`                                 | 합성 원문·자료·처리 이력 294건                     |
| `data/github-issue-drafts.json`                    | 기존 GitHub 예시 등록 원문, 검색에는 사용하지 않음 |
| `data/github-bindings.json`                        | 선택적 외부 예시 ID/URL                            |
| `lib/issues.ts`                                    | 플랫폼 중립 계약, 원문 보존, 진행·완료·기억 추출   |
| `lib/issue-store.ts`                               | 사용자별 D1 저장, 생성 멱등성, revision CAS        |
| `lib/issue-search.ts` / `lib/issue-history.ts`     | 검색·다단계 근거 수집, 원문과 분석 상태 분리       |
| `lib/memory-graph.ts` / `lib/gravity-layout.ts`    | 임시 작업/완료 기억 표현과 탐색 배치               |
| `lib/brief-contract.ts` / `lib/llm-server.ts`      | 서버 전용 AI 요청·출력 검증과 사용 제한            |
| `lib/memory-artifact.ts` / `lib/memory-service.ts` | 원문 밖 파생 기억, 벡터, 혼합 검색·연결            |
| `lib/github-import.ts`                             | GitHub REST 단방향 스냅샷 변환·페이지 안전성       |
| `db/schema.ts` / `drizzle/`                        | 파생 기억 D1 명시적 마이그레이션                   |
| `lib/llm-policy.ts`                                | 비밀이 없는 모델 선택 정책                         |

분류·평가 항목은 자유 문자열 키/값이다. 개별 입력 길이·개수 제한은 자원 보호용이며 고정 업무 분류 체계가 아니다.
관련 자료는 코드·문서·정책·양식·프로세스 모두 가능하다. seed의 `code:/`, `doc:/` 등은 합성 식별자이며 실제 파일·커밋 증거가 아니다.
발표용 정답 경로나 시나리오 재생 기능은 제품에 넣지 않았다.

대표 검증 사례는 과거 해결·롤백의 재사용(WS-008), 의도된 과거 소속 표시(WS-016), 타팀 시간대 변경의 사이드 탐색(WS-024)이다.
직접 검색에서 놓친 이슈도 실제 내용·자료의 다단계 연결로 탐색하도록 테스트하며, 답을 순위에 강제로 주입하지 않는다.

## 운영 경계와 남은 기능

Sites 게이트웨이가 주입·덮어쓰는 `oai-authenticated-user-id`를 신뢰하므로 별도 공개 Worker 주소로 우회 노출하면 안 된다.
DB 질의는 바인딩 파라미터와 사용자 ID 범위로 제한한다.
D1의 기존 이슈·요청 제한 테이블은 호환을 유지하고, 파생 기억 테이블은 Drizzle 명시적 마이그레이션으로 관리한다.

아직 구현하지 않은 범위:

- GitHub 웹훅·예약 동기화·양방향 쓰기 및 GitHub 외 실제 커넥터.
- 대규모 전사 벡터 저장소(Vectorize 등)와 재색인 작업 큐. 현재 D1 JSON 벡터 방식은 300건 POC 범위다.
- 조직 공동 작업공간, 팀 공유 권한, 자료별 ACL, 운영용 감사·커넥터 비밀 관리.
- 완료 기억 재개방·정정 워크플로, 대량 데이터 성능 검증, 운영 백업·복구 체계.

현재는 **개인별 POC 작업공간**이다. 실제 전사 40~50명 공유 서비스와 동일한 권한·운영 체계라고 주장하지 않는다.
