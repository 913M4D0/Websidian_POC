# Websidian POC 검색·그래프 벤치마크 프로토콜

## 1. 목적과 주장 범위

이 벤치마크는 `data/issues.json`의 합성 이슈 294건에서 평면 텍스트 검색과 현재 Websidian 검색·2-hop 탐색을 같은 기준으로 비교합니다. 대표 이슈 24건은 세 시나리오의 기준·관련 기록으로 사용하고, 나머지 270건은 배경 노드로 사용합니다.

이 결과가 증명하는 것은 **합성 시나리오에서의 검색·경로 회수 성능, 순위 기반 생산성 대리지표와 실행시간**입니다. 실제 현업 생산성, 시간·비용 절감, 장애 감소, 인과관계 정확도나 장기 사용성을 증명하지 않습니다. WS-008·WS-016·WS-024는 미해결 기준 이슈이므로 검색된 기록을 원인 또는 정답으로 표현하지 않습니다.

## 2. 데이터 동결

- 기준 데이터: `data/issues.json`
- 예상 데이터: 합성 이슈 294건, 완료 251건, 진행 43건
- 대표 범위: `WS-001`~`WS-024`
- 배경 범위: `WS-025`~`WS-294`
- 기준 이슈: `WS-008`, `WS-016`, `WS-024`

실행기는 원본 파일의 SHA-256, 현재 Git commit, Node·운영체제·CPU, 입력 파일 경로와 반복 횟수를 결과 JSON에 기록합니다. 원본 데이터나 제품 코드는 수정하지 않습니다.

## 3. 비교 방법

| 방법                | 실제 입력과 동작                                                                                                                         |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `baseline-text`     | 기준 이슈의 제목과 본문만 `searchIssues`에 전달합니다. 기준 이슈를 reference로 전달하지 않으므로 자료 식별자 유사도는 사용하지 않습니다. |
| `websidian-search`  | 제품의 `issueText`와 `searchCompletedIssues`를 그대로 사용합니다. 원문·자료·완료 기록을 사용하는 현재 평면 순위입니다.                   |
| `websidian-history` | 제품의 `buildHistory`를 그대로 사용합니다. 상위 직접 결과 최대 5건에서 완료 이력 이웃을 최대 2-hop으로 확장합니다.                       |

세 방법 모두 진행 중 기준 이슈 자체를 결과에서 제외하고 완료 이슈만 평가합니다. 알고리즘을 복사해 재구현하지 않고 현재 제품 모듈을 직접 import하므로 제품 변경은 다음 실행 결과에 반영됩니다.

## 4. 독립 정답과 순환 검증 방지

`ground-truth.json`은 대표 이슈 원문·자료·처리 기록을 읽어 작성한 평가 전용 qrels입니다. 제품 런타임이나 검색 순위에 주입하지 않습니다.

- `relevance`: 1~3등급 시나리오 관련성입니다.
- `expectedDirectIssueIds`: 현재 이슈에서 바로 확인할 가치가 있는 기록입니다.
- `expectedTwoHopPaths`: 중간 기록과 다음 기록의 원문·자료 연결이 모두 설명 가능한 경로입니다.
- hop은 탐색 기대치이지 사실 관계나 인과 단계가 아닙니다.

특히 WS-006의 기대 경로는 현재 엔진이 선택하는 `WS-007 → WS-006`이 아니라 원문상 더 강한 장애·롤백 연결인 `WS-005 → WS-006`으로 고정했습니다. 따라서 현재 결과를 정답으로 복사해 만점을 만드는 평가가 아닙니다.

## 5. 실행

프로젝트 루트에서 실행합니다.

```powershell
node --experimental-strip-types scripts/eval-retrieval.mjs
```

기본 출력은 `evidence/poc-benchmark/results/`에 생성됩니다.

```powershell
node --experimental-strip-types scripts/eval-retrieval.mjs `
  --iterations 100 `
  --output-dir evidence/poc-benchmark/results
```

지원 옵션:

- `--issues <path>`: 이슈 JSON 경로
- `--tasks <path>`: 과제 정의 경로
- `--ground-truth <path>`: 정답 경로
- `--output-dir <path>`: CSV·JSON 출력 폴더
- `--iterations <1..10000>`: 방법·과제별 시간 측정 반복 횟수, 기본 50회

## 6. 출력

- `retrieval-eval.json`: 데이터·환경 해시, 지표 정의, 과제별 순위·경로·시간 표본, 방법별 집계
- `retrieval-eval.csv`: 과제×방법 단위의 발표·분석용 평면 표

실행시간은 5회 warm-up 뒤 `performance.now()`로 측정하며 p50·p95를 기록합니다. 동일 PC에서 비교할 상대 지표이며 다른 장비의 절대시간과 직접 비교하지 않습니다.

## 7. 해석과 보고

1. Recall@5/10과 MRR은 관련 기록을 얼마나 빨리 회수했는지 보여줍니다.
2. nDCG@5/10은 핵심 관련 기록을 위에 배치했는지 보조적으로 보여줍니다.
3. direct path recall은 기대 직접 기록이 실제 depth 1로 제시됐는지 측정합니다.
4. 2-hop target recall은 기대 원거리 기록을 depth 2에서 찾았는지 측정합니다.
5. 2-hop path recall은 허용된 중간 기록까지 일치했는지 더 엄격하게 측정합니다.
6. distractor 오탐률은 Top-K 슬롯 중 시나리오 비관련 이슈 비율입니다. 전체 음성 집합 대비 통계학적 FPR가 아니라 false-discovery 성격의 지표입니다.
7. background-270 비율은 그중 `WS-025`~`WS-294` 배경 노드가 차지한 비율입니다.
8. 첫 grade-3 근거까지 확인 문서 수는 첫 핵심 근거의 순위이고, 모든 grade-3 근거까지 필요한 문서 수는 핵심 근거 중 가장 뒤의 순위입니다. 미회수 핵심 근거가 있으면 후자는 빈 값과 누락 ID로 기록합니다.
9. Top-10 유효근거 밀도는 반환 슬롯 중 grade 1~3 관련 기록의 비율이며, grade-3 coverage@10은 핵심 근거 전체 중 Top-10에서 찾은 비율입니다.
10. LLM 문맥 건수 비율은 실제 `buildIssueInsightContext`가 고른 완료 이력 수를 전체 완료 이력 251건으로 나눕니다.
11. LLM 문맥 문자수 비율의 분자는 실제 `buildIssueInsightContext` 직렬화 결과입니다. 분모는 같은 발췌 길이·필드로 완료 이력 251건을 모두 투영한 비교용 JSON이며 실제 모델로 보내지 않습니다. 문자수 비율은 토큰·비용 비율이 아닙니다.

8~11번은 모두 **생산성 대리지표(proxy)** 입니다. 읽는 문서 수가 줄었다는 결과를 실제 조사시간, 업무시간 또는 비용 절감률로 환산하지 않습니다. 사람 참여 실험 없이 사용할 수 있는 표현은 `합성 데이터에서 핵심 근거가 더 앞에 나타났다`, `LLM 입력 후보를 N건에서 M건으로 줄였다`까지입니다.

결과를 발표할 때는 데이터 SHA-256, commit, 실행일, 반복 횟수와 함께 제시합니다. 지표가 낮은 항목은 숨기거나 정답을 바꾸지 않고 제품 개선 후보로 기록한 뒤 새 버전으로 다시 실행합니다.

## 8. 재검토 원칙

qrels는 두 명 이상의 검토자가 제품 순위를 보지 않은 상태에서 원문 근거로 독립 검토하는 것이 이상적입니다. 합의로 등급이나 허용 경로를 바꾸면 변경 이유·검토자·일자·버전을 남기고, 이미 본 결과에 맞춘 변경은 별도 버전으로 취급합니다.
